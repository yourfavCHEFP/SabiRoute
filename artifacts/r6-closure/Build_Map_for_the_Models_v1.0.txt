# 0. Purpose and operating contract

This is the controlling execution brief for every model contributing to the remainder of SabiRoute R6.0.

Read it completely before acting. Inspect the live repository and current evidence. This map records known decisions and constraints; it does not replace live verification.

**Core principle: SabiRoute decides. LiteLLM executes. Evidence guides the path.**

**Mandatory principle: Treat failures as architectural evidence.**

Preserve failures, investigate their causes and distinguish architecture defects from implementation errors, stale evidence, environment problems, permissions and governance restrictions. Never bypass a failure merely to make a run green.

### 0.1 Status vocabulary

Every model must distinguish:

- **Selected:** owner chose an option.
- **Approved:** owner explicitly authorised a decision or action.
- **Implemented:** code or documentation was changed.
- **Tested:** a check actually ran.
- **Independently verified:** another authorised actor reviewed the evidence.
- **Gate accepted:** owner explicitly accepted the exit gate.

These states are not interchangeable.

### 0.2 Collaboration roles

| Role | Actor | Responsibility |
|---|---|---|
| Owner | User | Architecture decisions, approvals, scope and gate acceptance |
| Primary builder / registrar | Claude Code Terminal | Repository execution, edits, tests and registrar duties |
| Collaborative builder | Claude Code Desktop | Coordinates execution and collaborates with terminal Claude Code |
| Independent verifier | VS Code GitHub Copilot | Read-only independent verification |
| Recovery support | Copilot when not verifying | Investigations and repairs under explicit authority |

Claude Code Terminal and Claude Code Desktop are both builders. They must work together using this build map.

Neither Claude Code instance may claim independent verification of work it authored or materially directed.

Copilot is the independent verifier. It must not verify its own changes. If Copilot performs a repair, a fresh independent verification is required.

### 0.3 How many prompts until R6.0 closes?

Our target is **five controlled handoffs**:

1. **Build prompt:** Claude Code Desktop coordinates the remaining R6.0 work with Claude Code Terminal.
2. **Evidence prompt:** Terminal Claude Code produces consolidated test, digest, manifest and Git evidence.
3. **Independent verification:** VS Code Copilot verifies the completed work read-only.
4. **Correction prompt:** Only if Copilot identifies concrete defects.
5. **Closure prompt:** Owner reviews the evidence and decides BL-22, G7 and formal R6.0 acceptance.

This is a planning target, not permission to skip gates. Safe work packages should be consolidated rather than turned into dozens of exploratory prompts.

This build map closes R6.0 only. It must not start these implementation phases.

### 2.2 Non-negotiable constraints

1. Preserve immutable original request.
2. Make canonical representation and metadata explicit.
3. Policy/capability checks precede transformation.
4. Preserve explicit bypass.
5. Keep compression separate from routing policy.
6. Transform once before the provider-attempt loop, not once per retry.
7. Preserve original reservation estimate.
8. Never silently re-baseline reservations.
9. Unknown usage uses the full original estimate for budget and quota.
10. No prompt text logging or persistence.
11. No provider-specific prompt mutation without explicit policy.
12. Do not adopt `litellm.compress()` without source-level inspection of installed LiteLLM and its dependencies.
13. Seven-mode vocabulary is discovery terminology only.
14. No production/customer-readiness claims without evidence.

### 2.3 Registration and verification architecture

- REG and VER are distinct acts.
- REG is adjacent to the canonical T16 entry only where the protocol defines a valid locus. O1–O5 locus must be resolved before registration.
- VER uses a separate append-only JSONL ledger.
- Canonical JSON per line.
- Chained entries use `seq`, `prev`, `entry_sha256` and approved `entry_type`.
- Genesis uses the approved nine-field schema and UUIDv4 ledger ID; domain-separated.
- Each successfully appended VER entry receives a trusted checkpoint.
- Checkpoint independently preserved/authenticated outside the mutable workspace.
- Selected free approach: OpenSSH Ed25519 detached signature and owner-controlled private key; verifier uses public key only.
- Public repository may host public registration evidence. Require offline copy plus independent cloud copy. Cloud sync alone is not immutable.
- No automatic stale-lock deletion/recovery. Require explicit authority, retain evidence and fail closed on contention.
- No fabricated historical accounting IDs or backfill.
- No ledger or registration instantiation until owner authorises the act and prerequisites are satisfied.

# 5. Failure handling — mandatory

When a test, gate, tool, schema, workflow or model action fails:

1. Preserve the exact error and context.
2. Identify the layer: architecture, policy, implementation, test fixture, environment, permission, evidence or governance.
3. Determine whether it exposes a design flaw, missing invariant, stale evidence, environmental limitation or real regression.
4. Never bypass it to make the run green.
5. Never weaken tests or thresholds to fit current behaviour.
6. Propose the smallest correction consistent with approved architecture.
7. Identify whether the correction is authorised or requires an owner decision.
8. Add a regression test or durable evidence where appropriate.
9. Rerun affected checks.
10. Record the failure and resolution in the build report.

Permission denial is neither proof an action is unsafe nor permission to use an unapproved workaround.

A failing test is not automatically a product defect. Investigate first.
